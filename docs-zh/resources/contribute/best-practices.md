# 贡献最佳实践

以下是项目实际强制执行的约定。遵循与否，决定了评审是关于你的修改本身，还是关于格式。

## 写代码之前

**任何非平凡的需求先讨论。** 一个功能通常有多种合理的设计方案，而比较它们成本最低的地方是[讨论](https://github.com/conductor-oss/conductor/discussions)，而不是一个已经完成的工作拉取。用代码展示想法是受欢迎的——只是要知道它可能是白做的工作。

**考虑它是否属于核心。** 并非每个功能都属于核心。权衡以下几点：

- 它是否为不需要它的用户增加了复杂度或困惑？
- 它是否破坏向后兼容性？这很少可被接受。
- 它是否为某个核心模块引入了依赖？这很少可被接受。
- 它应该是可选启用的吗？新的队列或持久化后端应放在一个独立的、可选项启用的模块中。
- 它是否应该完全独立为单独的仓库？与其他系统的集成往往应该如此，因为它们的生命周期与服务器不同。

## 代码风格

- **提交前运行 Spotless。** `./gradlew spotlessApply`。CI 会在格式问题上失败，而纯格式化的 diff 会淹没真正的修改。
- **面向接口设计。** Conductor 在设计上就是可插拔的；新概念应以接口形式引入，实现位于接口之后。
- **尊重模块边界。** DAO 接口属于 `core`。实现属于各自的持久化模块——`postgres-persistence`、`redis-persistence` 等等。`core` 中的类不得深入某个特定后端。
- **遵循周边代码的风格。** 与你正在编辑的文件在命名、结构和注释密度上保持一致，而不是引入另一套风格。
- **为不显然之处写注释。** 解释算法、顺序约束、某个检查存在的原因。跳过只是复述代码的注释。
- 代码、日志或注释中**不使用 emoji**。

## 测试

- **避免使用 mock。** 尽可能使用真实实现。基于 mock 构建的测试往往是在断言 mock 被调用了，而不是断言代码正确工作。
- **测试行为，而非结构。** 重新实现其检查逻辑的测试会以错误的原因通过，并在实现被重构时失败。
- **使用 Testcontainers** 处理数据库、缓存和其他外部依赖。
- **覆盖并发场景。** 引擎的很大一部分是多线程的；单线程测试会漏掉它最重要的失效模式。
- 在推送之前，**`./gradlew test` 必须通过**。

有一点值得内化：有些 bug 只在跨越进程边界时才会出现。某个行为在进程内测试中正常工作，但在部署的服务器上仍可能是坏的，因为测试与被测代码共享文件系统、JVM 和时钟。如果修改触及跨越该边界的内容，请用集成测试或端到端测试来证明它。

## 依赖锁定

有些依赖是被有意锁定的，不应例常升级。仓库根目录的 `AGENTS.md` 记录了当前的硬性锁定及每一项的原因，以及修改前应检查什么。在添加或升级依赖之前先阅读它——在不相关的 pull request 中顺手的版本升级，是收到“要求修改”的常见原因。

## Pull Request

- **以 `main` 为目标。** 它是稳定分支，也是唯一的 PR 目标。
- **每个 PR 只做一个逻辑修改。** 聚焦的 diff 能一遍评完；一个既修 bug、又重排格式、还升级 Gradle 的 PR 会卡住在那部分没人要求的内容上。
- 任何代码变更都要**添加或更新测试**。
- 推送前**运行 `./gradlew spotlessApply` 和 `./gradlew test`**。
- **写描述性的提交信息。** 说明改了什么、为什么改。原因（why）是读者无法从 diff 中重建的部分。

评审可能需要时间。项目成员分布在不同时区，维护者还有其他工作——延迟并不意味着不感兴趣。

## 文档

文档是从源码推导而来的，而非凭记忆编写。要记录一个端点，打开 controller，从其映射注解中复制路径。要记录一个 CLI 参数，打开命令并阅读其参数声明。要展示输出，实际运行一遍并粘贴它打印的内容。

如果你无法验证某个示例——没有可用的服务器、没有凭据——用 `<!-- TODO: verify against live server -->` 标记它，并在 pull request 中说明，而不是让一个未经验证的示例看起来像已验证的。

仓库根目录的 `CLAUDE.md` 有按内容类型划分的检查清单，以及每种页面的源码位置。
