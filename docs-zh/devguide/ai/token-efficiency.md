# 持久化执行的 Token 效率

LLM 调用是昂贵的。每个 token 都要花钱，而每次重新执行都在燃烧已经付过费的 token。持久化执行通过保证已完成的工作永远不会丢失，从而消除浪费的 token。


## 没有持久化的崩溃代价

考虑一个运行 20 步循环的自主 agent。每次迭代调用一次 LLM（规划）和一个工具（执行）。agent 在第 18 次迭代时进程崩溃。

**没有持久化执行时：**

agent 从第 1 次迭代重新开始。第 1-17 次迭代必须重新执行 — 17 次 LLM 调用产生与之前完全相同的输出。Token 被再次燃烧，工具调用被重新执行（可能产生重复的副作用），用户为已经完成的工作再次等待。

**使用 Conductor 时：**

agent 从第 18 次迭代恢复。第 1-17 次迭代已经持久化 — 它们的 LLM 输出、工具结果和状态都在持久化存储中。零 token 浪费。零重复工具调用。agent 精确地从它停下的地方继续。


## token 在哪里被节省

### 1. 崩溃恢复

Conductor 工作流中的每个 LLM 调用都在完成时持久化。Prompt、响应、token 用量和模型都会被记录。如果服务器、工作者或网络失败：

- 已完成的 LLM 调用**永远不会重新执行**。它们的输出从存储中读取。
- 只有进行中的调用会被重试 — 而且只有那一个调用。
- 工作流从最后持久化的状态恢复。

**Token 节省：** 与 agent 崩溃前推进了多远成比例。一个在第 20 步中的第 18 步崩溃的 agent 节省了 17 次 LLM 调用的 token。

### 2. 从失败任务重试

当工作流失败时（例如 LLM 规划成功后某个工具调用返回了错误），你可以[从失败的任务重试](../../architecture/durable-execution.md#replay-and-recovery)。Conductor 复用所有之前已完成任务的输出。

**示例：** 一个 5 任务的工作流在第 4 个任务（工具执行）失败。任务 1-3 包含两次 LLM 调用，共消耗 8,000 个 token。从任务 4 重试：

- 任务 1-3 **不会重新执行**。它们的输出（包括 LLM 响应）从存储中复用。
- 只有任务 4（及其后的所有任务）重新执行。
- 每次重试**节省 8,000 个 token**。

### 3. 从特定任务重跑

当你修复了某个任务定义中的 bug 并[从该任务重跑](../../architecture/durable-execution.md#replay-and-recovery)时，它之前的所有任务都保留其持久化输出。上游的 LLM 调用不会重新执行。

### 4. 循环检查点与重试边界

agent 循环（`DO_WHILE`）对每次迭代做检查点。如果基础设施在工作流仍处于活跃状态、进行到第 50 次迭代中的第 48 次时恢复：

- 第 1-47 次迭代连同它们的所有 LLM 调用和工具结果一起被持久化。
- 只有第 48 次迭代重新执行。
- **节省 47 次迭代的 LLM token。**

这与重试一个失败的 `DO_WHILE` 不同：对失败循环的重试会从第 1 次迭代重新开始它的迭代历史。让工具保持幂等、给循环设置边界，并保留让该重启安全所需的上下文。


## 真实世界的成本影响

下面是一个使用典型 LLM 定价的具体示例：

| 场景 | 没有持久化 | 使用 Conductor | 节省 |
|----------|-------------------|----------------|---------|
| 20 步 agent，在第 18 步崩溃 | 重跑全部 20 步：约 40K token | 从第 18 步恢复：约 4K token | **约 36K token（$0.04-$0.40）** |
| RAG 管道在 PDF 生成处失败 | 重跑嵌入 + LLM：约 12K token | 只重试 PDF 步骤：0 LLM token | **约 12K token（$0.01-$0.12）** |
| 100 次迭代循环，在第 95 次崩溃 | 重跑全部 100 次：约 200K token | 从第 95 次恢复：约 10K token | **约 190K token（$0.19-$1.90）** |
| 带人工审批的 agent，审阅者较慢 | 进程可能超时并重启 | HUMAN 任务无限期持久化 | **上游所有 token 被保留** |

这些是单次执行的节省。乘以每天数千次执行，成本差异就会变得显著。

在大规模场景下 — 每天数千次 agent 执行 — 即使只有 5% 的崩溃/重试率，在没有持久化时也会转化为可观的 token 浪费。使用 Conductor，这种浪费降到接近零。


## 崩溃之外的 token 节省

持久化执行在崩溃之外的场景也节省 token：

**带 Human-in-the-loop 的长时运行 agent。** 一个 HUMAN 任务可以暂停工作流数小时或数天。没有持久化时，进程可能超时或被杀掉，需要完全重启（并重新运行所有上游 LLM 调用）。使用 Conductor 时，暂停是持久的 — 工作流精确地从停下的地方恢复，所有 LLM 输出都被保留。

**部署与扩缩容。** 当你部署 worker 的新版本或缩减实例时，在途的工作流会存活。没有任何 LLM 调用丢失。没有持久化时，扩缩容事件可能在执行中途杀掉进程，浪费到目前为止消耗的所有 token。

**调试与迭代。** 调试一个失败的 agent 时，你可以检视每个 LLM prompt 和响应而无需重跑 agent。从特定任务重跑来测试修复，而无需重新执行（也无需重新付费）上游 LLM 调用。


## 机制上如何工作

Conductor 持久化 LLM 任务输出的方式与持久化任何任务输出的方式相同：

1. `LLM_CHAT_COMPLETE` 任务被调度，由一个工作者（或服务器本身）执行。
2. 收到 LLM 响应 — prompt、补全内容、token 用量、模型和延迟全部被记录。
3. 任务进入 `COMPLETED`，其输出在下一个任务被调度之前**写入持久化存储**。
4. 如果此后任何环节失败，LLM 输出已经持久化。它永远不会被重新执行。

这就是适用于 Conductor 中每个任务的同一个持久化模型 — [持久化执行语义](../../architecture/durable-execution.md) 保证已完成的工作永远不会丢失。


## 持久化执行在哪些地方减少重复工作

已完成任务的输出在基础设施恢复、暂停和任务级重试之后仍然可用。当某个下游任务失败、agent 等待审批、或操作者从选定的任务重跑时，这可以避免重复上游的 LLM 调用。

这不是"任何调用都不会再运行"的保证。Conductor 使用至少一次投递，且重试一个失败的 `DO_WHILE` 会重新开始该循环的迭代历史。让工具保持幂等，并有意识地选择重试边界。
