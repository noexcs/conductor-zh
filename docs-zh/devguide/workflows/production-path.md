# 持久化工作流的生产化路径

在你完成[第一个工作流](../../quickstart/first-workflow.md)之后使用本指南。它把一次成功的本地运行转化为一个具备显式契约、有界失败行为、可重复部署和运维模式的服务。

## 成果

你将拥有一个工作流：调用方了解它的输入和输出契约，它的任务带有审慎设置的可靠性配置，而运维人员知道如何检查和恢复一个执行。

## 1. 定义契约

把工作流定义及其 `outputParameters` 当作一个 API。记录必需的输入，在边界处校验或拒绝无效请求，并为调用方保持输出稳定。当某个变更不向后兼容时，注册一个新的工作流版本，而不是就地修改正在使用的定义。

在发布面向调用方的工作流之前，先阅读 [工作流定义](../concepts/workflows.md)、[任务输入](../how-tos/Tasks/task-inputs.md) 和 [工作流版本管理](../how-tos/Workflows/versioning-workflows.md)。

## 2. 让失败策略显式化

对每一个外部副作用，决定它是否可安全重试，以及如何使其幂等。审慎地设置任务的重试行为和超时；当后续失败需要业务回滚时，使用失败工作流或补偿。当业务操作有最长可接受时长时，为工作流本身设置上限。

通过强制制造一个瞬时任务故障来验证设计，并确认预期的重试、超时或补偿路径在执行中可见。

继续学习 [任务超时与重试](../cookbook/task-timeouts-and-retries.md)、[错误处理](../how-tos/Workflows/handling-errors.md) 和 [最佳实践](../bestpractices.md)。

## 3. 测试真实的边界

用有代表性的输入测试已注册的定义，而不要只孤立地测试工作者函数。覆盖成功、可重试失败、终态业务失败、超时，以及每个副作用的幂等行为。在可行的地方使用真实依赖或 Testcontainers，以验证队列、持久化和并发行为。

**验证：** 用一个测试关联 ID（correlation ID）启动工作流，检查它的完整执行，并断言其输出契约和终态状态。

## 4. 安全地部署定义和工作者

在把生产流量路由到某个工作流之前，先部署该工作流所需的工作者代码和任务定义。由于 Conductor 的投递是至少一次的，保持工作者幂等。发布新的工作流版本，审慎地更新调用方，并在旧版本的执行排空之前保留旧版本。

实现细节请使用 [创建工作流](../how-tos/Workflows/creating-workflows.md)、[扩展工作者](../how-tos/Workers/scaling-workers.md) 和 [部署](../running/deploy.md)。

## 5. 运维执行

为运维人员提供工作流名称、版本、关联 ID（correlation ID）约定和负责人。监控队列深度、任务失败、超时和执行状态。在事故期间，重试前先检查失败的任务；只重试可以安全重复的失败，然后根据业务策略暂停、恢复、重跑或终止。

**恢复演练：** 故意让一个工作流停留在等待状态，或让一个可重试任务失败，然后通过 [搜索工作流](../how-tos/Workflows/searching-workflows.md) 找到它，并用已文档化的 [调试](../how-tos/Workflows/debugging-workflows.md) 手段恢复它。
