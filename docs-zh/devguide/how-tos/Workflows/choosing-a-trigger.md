# 选择工作流触发器

选择其所有者能够可靠地做出启动或恢复决定的机制。

| 需求 | 使用 | 结果 |
|---|---|---|
| 请求应立即创建工作 | [直接启动](starting-workflows.md) | 一个新的工作流执行 |
| 按时间或周期创建工作 | [定时计划](scheduling-workflows.md) | 每个 cron 时段一个执行 |
| 由 broker 消息创建工作 | [事件处理器](../../../documentation/configuration/eventhandlers.md) | 每个匹配事件的执行 |
| 父工作流拥有该依赖 | `SUB_WORKFLOW` 或 `START_WORKFLOW` | 子执行，可等待或即发即忘 |
| 外部结果应恢复已有工作 | 任务信号或事件处理器的 `complete_task`/`fail_task` | 指定任务改变状态 |

## 决策步骤

1. 判断该操作是创建新的执行，还是恢复已有执行。
2. 如果是创建工作，识别所有者：应用请求、时钟、消息或父工作流。
3. 如果是恢复工作，在任务开始等待时保留任务 ID 或工作流 ID 及任务引用名称。
4. 在启用重试或 broker 重发之前，定义幂等键或稳定的消息 ID。
5. 验证可观察的结果：启动时返回工作流 ID，恢复时检查预期的任务状态和下游转移。

## 限制

- 定时计划没有原生的重叠策略；执行可能重叠。
- 事件操作是并发且非原子的；一个可能成功，另一个失败。
- OSS 事件处理器无法将业务关联键解析到等待中的任务。
- 信号改变已有工作；它不会创建新的工作流。

接下来，使用[启动工作流](starting-workflows.md)、[定时计划工作流](scheduling-workflows.md)或[事件编排](../event-bus.md)实现所选路径。
